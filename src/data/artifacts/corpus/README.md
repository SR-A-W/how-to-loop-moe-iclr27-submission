# Probe-corpus artifacts

The raw-text files here are generated by
`scripts/data/prepare_corpus.py` from `NeelNanda/pile-10k` (deterministic selection:
original dataset index order, domain whitelist, max N docs per domain, min-chars
floor, no random sampling — see that script's docstring), except
`pile10k_B_d50_b500_s512.json`, whose generation method is documented in its own
section below. Loaded by `src/data/probe_corpus.py`.

### Domain-list difference from the 40-doc corpus, and why

**`Books3` is replaced by `Wikipedia (en)`.** In `NeelNanda/pile-10k`, at this
generator's `min_chars=4096` threshold, `Books3` has only **9** qualifying
documents — nowhere near the 50/domain this corpus needs (checked directly
against the dataset, not estimated). All other 9 domains comfortably clear 50
at the same threshold (lowest: ArXiv, 86). Those 9 Books3 documents still exist
in the dataset and could be used for something needing exactly ≤9 docs, but
they cannot support a 50-per-domain design.

Design choice: keep the 10-domains-balanced-at-50 structure rather
than force the same domain set as the 40-doc corpus — the new corpus is meant
to become the primary 500-doc probe corpus in its own right (the 40-doc one
stays frozen and reproducible under its own id), so an internally consistent
10×50 balance matters more than matching the old domain list exactly.
`Wikipedia (en)` was picked as the replacement: 779 qualifying documents at the
same threshold, comfortably clears 50.

### Generation command (exact parameters; run offline against a local Hugging Face cache)

```bash
export HF_HUB_OFFLINE=1
python scripts/data/prepare_corpus.py \
  --out src/data/artifacts/corpus/pile10k_d50_b500_s512.json \
  --n-docs 500 \
  --min-chars 4096 \
  --max-per-domain 50 \
  --domains "ArXiv,Wikipedia (en),DM Mathematics,FreeLaw,Github,OpenWebText2,Pile-CC,PubMed Central,StackExchange,USPTO Backgrounds"
```

### Acceptance checks run against the produced file (content, not just exit code)

- Exactly 500 docs, exactly 50 per domain, 10 distinct domains (read back from
  the file's own `docs`/`provenance` fields).
- Every document tokenizes to **≥ 512 tokens** via the project's Llama-3
  tokenizer (`src.data.tokenizer.Llama3Tokenizer`, BOS+doc+EOS framing) —
  actual min across all 500 docs: **757 tokens** (max: 60,772).
- **0 duplicate documents** (500 distinct `sha256` values among 500 docs).
- **36 documents overlap** with the 40-doc corpus by `sha256` (all from the 9
  domains shared between the two corpora — `prepare_corpus.py`'s deterministic
  index-order selection means the 40-doc corpus's 4 picks per shared domain

  9 domains × 4 = 36, exactly matching). Not required to be 0 — reported as a
  fact for anyone who needs mutually-exclusive corpora.

## `pile10k_B_d50_b500_s512.json` — expert-masking eval's "corpus B"

Companion to `pile10k_d50_b500_s512.json` ("corpus A", the "500-doc corpus" section
above), for the expert-masking
evaluation: A picks the target expert set and B measures the loss after masking it, on
**document-disjoint** text from the same distribution.

- **485 documents** (not 500 — see "Why 485, not 500" below): `ArXiv` 36,
  `DM Mathematics` 49, the other 8 domains 50 each, `min_chars=4096`.
- sha256: `8dcd5d2fbfa723d5fd7e5c618e312b6eb0a4f5cedec86a6adbb358daae470115`
- Domains: same 10 as corpus A (ArXiv, DM Mathematics, FreeLaw, Github,
  OpenWebText2, Pile-CC, PubMed Central, StackExchange, USPTO Backgrounds,
  Wikipedia (en)).
- Referenced as `probe_corpus.LARGE_CORPUS_B_PATH` / `probe_corpus.LARGE_CORPUS_B_ID`
  (`pile10k_B_d50_b500_s512_v1`).
- **0 documents overlap with corpus A** (by `sha256`) — see generation method below.

### Generation method: same algorithm as `prepare_corpus.py`, plus one exclusion step

`prepare_corpus.py` has no built-in "skip documents already used elsewhere" option, so
corpus B was generated by a one-off script (`scripts/data/build_corpus_b.py`; a single-use
generator, not a reusable CLI flag; reproduced in full below)
that replicates `prepare_corpus.py`'s selection loop byte-for-byte (same dataset id/split,
same original-index-order scan, same `min_chars=4096`, same 10-domain whitelist, same
`max_per_domain=50` cap, same sha256-dedup) with exactly one addition: a document whose
sha256 is already in corpus A's `docs` is skipped. Because the scan order and every other
rule are unchanged, this deterministically collects **the next eligible documents per
domain after corpus A's picks** — corpus A's first 50 (or however many were available)
per domain, corpus B's next up-to-50.

```python
# build_corpus_b.py -- run against a local HF_HUB_OFFLINE cache of NeelNanda/pile-10k
import hashlib, json
from pathlib import Path
from datasets import load_dataset

DOMAINS = ["ArXiv", "Wikipedia (en)", "DM Mathematics", "FreeLaw", "Github",
           "OpenWebText2", "Pile-CC", "PubMed Central", "StackExchange", "USPTO Backgrounds"]
MIN_CHARS, MAX_PER_DOMAIN = 4096, 50

a = json.loads(Path("src/data/artifacts/corpus/pile10k_d50_b500_s512.json").read_text())
excluded_sha = {d["sha256"] for d in a["docs"]}  # corpus A's 500 documents

ds = load_dataset("NeelNanda/pile-10k", split="train")
picked, per_domain, seen_sha = [], {}, set()
for i, row in enumerate(ds):
    text = row["text"]
    if len(text) < MIN_CHARS:
        continue
    domain = (row.get("meta") or {}).get("pile_set_name", "unknown")
    if domain not in DOMAINS or per_domain.get(domain, 0) >= MAX_PER_DOMAIN:
        continue
    sha = hashlib.sha256(text.encode()).hexdigest()
    if sha in seen_sha or sha in excluded_sha:  # <-- the one addition over prepare_corpus.py
        continue
    seen_sha.add(sha)
    per_domain[domain] = per_domain.get(domain, 0) + 1
    picked.append({"name": f"{domain.replace(' ', '_')}#{i}", "domain": domain, "text": text,
                    "source_index": i, "sha256": sha, "n_chars": len(text)})
# per_domain now reads {"ArXiv": 36, "DM Mathematics": 49, ...: 50, ...} -- see below for why
```

Run with the same setup as corpus A's generation command above (`HF_HUB_OFFLINE=1`).

### Why 485, not 500: two domains are too small for a disjoint second batch

`prepare_corpus.py`'s selection is **deterministic and exhaustive** per domain (original
dataset index order, first N that qualify) — corpus A already took the first (up to) 50
qualifying documents in each domain, so corpus B's "next eligible documents" are limited
by how many qualifying documents that domain has **in total**, not by how many remain
after subtracting an assumed-large supply.

Measured directly against the dataset (not estimated), qualifying-document counts at
`min_chars=4096`:

| Domain | Total qualifying in `NeelNanda/pile-10k` | Taken by corpus A | Available for corpus B | Corpus B actual |
|---|---|---|---|---|
| ArXiv | **86** | 50 | 36 | 36 |
| DM Mathematics | **99** | 50 | 49 | 49 |
| Wikipedia (en) | 132 | 50 | 82 | 50 |
| StackExchange | 135 | 50 | 85 | 50 |
| FreeLaw | 161 | 50 | 111 | 50 |
| USPTO Backgrounds | 164 | 50 | 114 | 50 |
| Github | 245 | 50 | 195 | 50 |
| PubMed Central | 238 | 50 | 188 | 50 |
| OpenWebText2 | 461 | 50 | 411 | 50 |
| Pile-CC | 693 | 50 | 643 | 50 |
| **Total** | | 500 | | **485** |

Lowering `min_chars` does not fix this: at 2000/2500/3000/4096, ArXiv stays at 86-87 and
DM Mathematics stays at 99 — the dataset genuinely has few long documents in these two
domains, not an artifact of the 4096 threshold. No domain outside the existing 10-domain
whitelist reaches 50 qualifying documents either (the largest unused one,
`OpenSubtitles`, has 26), so there is no substitute domain that would restore an even
50/domain split without changing which domains are compared.

**Decision: take the 485-document corpus as-is** — record
the shortfall honestly (this section) rather than either lowering `min_chars` to force
more documents, or breaking the 50/domain balance by pulling extra documents from other
domains to reach 500. Rationale: pulling from other domains would make corpus A and
corpus B have different domain compositions, which is exactly the confound the
"same domains, disjoint documents" design exists to avoid; whereas 485 vs. 500 is a ~3%
difference in sample size, which only affects the variance of the expert-masking eval's
loss-difference measurements — an effect far smaller than what that evaluation is
designed to detect (the ρ metric of the expert-masking evaluation).

### Token-count consequence

The masking eval's probe-batch construction (`src.data.probe_corpus.build_probe_batch`,
`seq=512`) drops one uniform separator position per document, so corpus A's batch is
500 × 511 = **255,500** tokens and corpus B's is 485 × 511 = **247,835** tokens — not
equal, a direct consequence of the 485-vs-500 document count above, not a separate
discrepancy.
